## Что такое Yummi <a id="что-такое-yummi"></a>

Yummi состоит из **четырех компонентов и одного альтернативного интерфейса**, построенных вокруг строгого правила: *ИИ предлагает, шлюз исполняет.* Каждая команда пентеста, запускаемая ИИ, проходит ровно через одно место и контролируется сетевой политикой fail-closed, которая выдерживает любые сбои.

```
Пользователь / Оператор  →  Оркестратор (Go)  →  Шлюз (Rust, IPC)  →  Песочница (Kali Docker)
    Web UI / TUI            дирижер + агент      fail-closed nftables     только выполнение утилит
                            знания + API         движок политик + аудит
```

- **orchestrator** (Go) — управляет ИИ-дирижером, графовым движком агента, хранилищем знаний и REST/WebSocket API. Никогда не обращается к nftables напрямую.
- **gateway** (Rust, бинарный файл `yummi-gateway`) — единственный компонент, который может открывать исходящий трафик из песочницы. При запуске устанавливает правила nftables `DROP`-all; если шлюз падает, эти правила сохраняются в ядре (**fail-closed**).
- **sandbox** (Kali Docker) — файловая система только для чтения, бесправный пользователь (non-root), только привилегии `NET_RAW`/`NET_ADMIN`. Пассивный режим: выполняет действия только тогда, когда оркестратор запускает в нем `docker exec`.
- **ui** (React 18 + Vite) — веб-панель управления на порту `:3000`, проксирует `/api/` и `/ws/` на оркестратор на порту `:9080`.
- **TUI** (Charm Bubble Tea) — консоль оператора полностью в терминале (`yummi --tui`), работающая с тем же API REST/WS.

## Архитектура системы <a id="архитектура-системы"></a>

```text
        ┌──────────────────────────────────────────────────────┐
        │            Веб-панель      ·       Терминал TUI      │
        └───────────────────────────┬──────────────────────────┘
                                    │  REST + WebSocket · :9080
        ┌───────────────────────────▼──────────────────────────┐
        │ ОРКЕСТРАТОР · Go                                     │
        │                                                      │
        │   API ─▶ дирижер ─▶ граф агента ─▶ исполнитель       │
        │                          │                           │
        │                          ▼  (общая модель мира)      │
        │          Хранилище знаний: находки · память          │
        │                          · контекст · TRACE          │
        └───────────────────────────┬──────────────────────────┘
                                    │  Unix socket · JSON IPC с префиксом длины
        ┌───────────────────────────▼──────────────────────────┐
        │ ШЛЮЗ · Граница доверия на Rust                       │
        │ fail-closed nftables · выход · аудит · watchdog      │
        └─────────────┬────────────────────────────┬───────────┘
          docker exec │  ◀── ЕДИНСТВЕННЫЙ путь      │ контролируемый выход (egress)
        ┌─────────────▼───────────┐      ┌──────────▼───────────┐
        │ ПЕСОЧНИЦА · Kali        │      │  Внешние цели        │
        │ только чтение · non-root│      │  (согласно политикам │
        │                         │      │        шлюза)        │
        └─────────────────────────┘      └──────────────────────┘
```

Сигнал идет строго по одному позвоночнику — оператор → API → дирижер → агент → исполнитель → шлюз → песочница. `docker exec` — это **единственный путь** из доверенной зоны в песочницу, находящийся на логическом уровне после проверки шлюзом; песочница взаимодействует с внешним миром *исключительно* через правила nftables шлюза. Хранилище знаний подключено к агенту в качестве его общей модели мира.

### Сетевая топология

```
yummi_internal (172.20.0.0/24): песочница .10 · шлюз .2 (также DNS) · оркестратор .3 · ui .4 · docker-proxy .5
yummi_external:                 шлюз · оркестратор · только ui — песочница намеренно исключена.
                                Ее единственный путь наружу лежит через правила nftables шлюза.
Порты хоста: 3000 → ui nginx · 9080 → API оркестратора (только localhost)
```

DNS для песочницы принудительно направляется через шлюз (`172.20.0.2`), поэтому каждый запрос логируется.

## Граница доверия <a id="граница-доверия"></a>

Это **единственный самый важный инвариант** в кодовой базе: *запрещено все, что явно не разрешено.*

- Шлюз устанавливает правила nftables `DROP`-all **до** того, как откроется его IPC-сокет. У песочницы нулевая сетевая связность, пока не поступит явное правило `Allow`.
- Если процесс шлюза умирает, правила `DROP` остаются в ядре — система переходит в режим **fail-closed (закрыта при сбое)**, но никогда не остается открытой.
- **Правила блокировки (Block) всегда приоритетнее правил разрешения (Allow).**
- Команды пентеста попадают в шелл **ровно через одно место**: `sandbox.Bridge.Exec`, который запускает `docker exec --user 1000:1000 <container> /bin/bash -lc <cmd>`. Агент никогда не вызывает `exec.Command` самостоятельно — он только ставит команды в очередь выполнения, которую обрабатывает исполнитель (проверка шлюзом → запуск в песочнице). Команды на стороне хоста никогда не могут быть вызваны через вывод агента или LLM.

> Модуль шлюза работает внутри Docker, а не на хост-системе, используя поддержку ядра контейнерной среды. Прямой запуск скомпилированного бинарного файла на хосте macOS (вне Docker) не имеет необходимого ядра Linux для применения правил.

## Безопасность на уровне контента <a id="безопасность-на-уровне-контента"></a>

Шлюз отлично защищает систему на **сетевом уровне**. Однако дирижер пентеста сталкивается со вторым, более тонким вектором атаки: **контентом**, который поступает *обратно* в промпт LLM. Вывод команд цели, спарсенная веб-страница, ответ MCP — оператор не является автором этих данных, и любые из них могут содержать инъекцию промпта (`ignore previous instructions…`), команды C2/promptware, нагрузку для кражи данных или невидимые bidi-символы Unicode. Yummi распространяет архитектуру fail-closed и на этот уровень контента.

```text
    вывод утилит · запись в память · файлы навыков    (создано НЕ оператором)
                       │
                       ▼
             ┌───────────────────┐   threatscan: инъекции · кража · C2
             │     threatscan    │               · невидимый Unicode
             └─────────┬─────────┘
        вывод утилиты  │   запись в ПАМЯТЬ / загрузка навыков
      (нельзя прервать │   (через подтверждение пользователя)
       посередине)     │
               ▼                ▼
    ⚠ предупреждение      ⛔ блокировка в строгом режиме (strict)
    "untrusted DATA"
               │
               ▼
          промпт LLM
```

- **`internal/security/threatscan`** — листовой пакет (только стандартная библиотека), который сканирует данные в трех режимах (`all` / `context` / `strict`). Вывод утилит **сканируется и помечается предупреждающим баннером** (только обнаружение, без блокировки — оператор не может вмешаться в середине выполнения команды); операции записи `[REMEMBER]` и загрузки навыков **блокируются** в строгом режиме (strict), чтобы зараженный вывод не мог внедрить постоянную межсессионную инъекцию. Он также вырезает **ANSI/C1 управляющие последовательности** из вывода до того, как они попадут к модели.
- **Происхождение памяти** — каждая строка в постоянной памяти записывает ее автора (`agent` / `subagent`) для последующего аудита.
- **Тесты архитектурного соответствия** (`internal/security/invariants`) — исполняемые проверки, которые сканируют исходный код и **ломают сборку**, если `os/exec` используется за пределами разрешенных файлов шелл-границы, если `internal/mcp` импортируется в рабочем коде (блокировка неиспользуемого кода) или если обнаруживаются следы телеметрии. Нижеописанные инварианты проверяются автотестами, а не просто задокументированы.

## Движок агента <a id="движок-агента"></a>

Агент Yummi — это **не простой цикл `while`**. Это явный **графовый конечный автомат**: LLM на каждом шаге выдает ровно одно помеченное действие, а детерминированный роутер обходит типизированные узлы согласно фиксированной таблице ребер до тех пор, пока не будет достигнут конечный узел. Такой дизайн предотвращает переполнение контекста и бесконечные циклы действий — каждый шаг заново отрисовывает полное состояние задачи в промпте вместо того, чтобы полагаться на хрупкую историю диалога.

### Графовый конечный автомат — узлы и ребра <a id="графовый-конечный-автомат"></a>

Движок находится в `orchestrator/internal/agent`. В файле `graph.go` описан набор узлов и таблица маршрутизации `graphEdges` (`node → edge → nextNode`); каждый узел вынесен в собственный файл `node_*.go`.

**Десять узлов:**

| Узел | Файл | Ответственность |
|------|------|----------------|
| `step` | `node_step.go` | Запрашивает у LLM следующее действие; рендерит в промпт полное состояние задачи + НАВЫКИ + ДЕЛЕГИРОВАНИЕ + ПАМЯТЬ; маршрутизирует на основе возвращенного управляющего тега. |
| `tool` | `node_tool.go` | Проверяет, фильтрует и выполняет команду из буфера; обнаруживает зависания и повторы; контролирует длительно выполняющиеся команды. |
| `consult` | `node_consult.go` | Консультация во время выполнения (например, при долгой работе) — запрашивает у LLM `[CONTINUE]`/`[ABORT]`. |
| `retry` | `retry.go` | Восстановление после ошибок парсинга/LLM с экспоненциальной задержкой; возвращает к вызывающему узлу или сдается. |
| `summarize` | `node_lifecycle.go` | Сжатие контекста: когда лимит токенов исчерпан на ≥80%, сжимает историю наблюдений в краткую сводку. |
| `approval` | `node_lifecycle.go` | Точка подтверждения оператора (блокирует горутину цикла на канале). |
| `finish` | `node_lifecycle.go` | Конечный узел: завершено / не удалось / остановлено; генерирует сводку, если модель этого не сделала. |
| `ask` | `node_lifecycle.go` | Конечный узел: пауза и запрос вопроса оператору. |
| `handoff` | `node_handoff.go` | Делегирует сфокусированную подзадачу профильному субагенту и возвращает его отчет. |
| `remember` | `node_remember.go` | Записывает структурированную память (например, карту кода) в хранилище знаний. |

**Обход графа** (`Execute` в `graph.go`) — каждый рабочий узел возвращает управление на `step`, то есть движок и есть этот цикл; выход происходит только на конечных узлах:

```text
                     (каждый рабочий узел возвращается на STEP)
        ┌────────────────────────────────────────────────────────────┐
        │                                                            │
        ▼               run_command          ok / is_error           │
    ┌─────────┐ ─────────────────────────▶ ┌──────┐ ──────────────────┤
    │  STEP   │                            │ TOOL │                   │
    │ запрос  │ ◀───── PLAN_UPDATED ─────  │ exec │── требуется подтверждение ──▶ approval ─▶ STEP
    │ действия│                            │  +   │── долгая команда ──────────▶ consult  ─▶ STEP
    │ у ИИ    │                            │ guard│── зависание / цикл ────────▶ consult  ─▶ STEP
    └────┬────┘                            └──────┘
         │  finish · лимит исчерпан ──▶ FINISH  (конечный)
         │  ask_operator · стоп ─────▶ ASK     (конечный)
         │  llm_error ──▶ retry ──▶ (возврат к вызывающему)
         │  summarize · remember · handoff ──▶ (возврат на STEP)
         ▼
    Каждый шаг STEP заново собирает ПОЛНОЕ состояние задачи (план · наблюдения ·
    НАВЫКИ · ПАМЯТЬ) в промпте — а не передает сырую историю чата.
```

Конечные узлы (`finish`, `ask`) не имеют исходящих ребер — `Execute` останавливается при их достижении. Узел `retry` динамически возвращает к тому узлу, который его вызвал. Каждый переход сохраняется в контрольной точке, поэтому прерванная задача возобновляется с последнего узла.

**Предотвращение циклов многоуровневое** (узел `tool`): детекция идентичных повторов (`[DUPLICATE_BLOCKED]`), плавающий детектор зависаний для циклов `A→B→A→B` (`[STUCK]`), защита **tool-thrash**, ловящая семантически похожие команды, которые не совпадают по хэшу — например, чередование `ps -ef` / `ps -ejH` / `ps aux` (`[ABNORMAL_PATTERN]`), и эскалация последовательных ошибок, заставляющая сменить подход (`[REPEATED_FAILURE]`) перед тем как остановиться и передать управление оператору. Важно, что процедурная память никогда не возвращает команды, уже выполненные *в рамках текущей задачи*, поэтому цикл обучения не может усилить повторение.

### Протокол тегов <a id="the-tag-protocol"></a>

Агент и LLM общаются на **закрытом языке разметки в квадратных скобках** (описан в реестре `Registry` в `protocol.go`). Это *не* свободный текст и *не* XML — это `[TAG]` на отдельной строке, после которого может идти JSON-тело. Реестр является единственным источником правды; описание протокола в промпте генерируется автоматически на его основе.

```text
   АГЕНТ (узел step)                                    LLM (модель)
        │  рендерит состояние задачи + НАВЫКИ · ПАМЯТЬ          │
        │  + описание протокола, затем спрашивает ─────────────▶│
        │                                                    │
        │◀──────────────── [RUN_COMMAND] {command, risk} ────│
        │                                                    │
        │  проверка · детекция повторов · лимиты             │
        │  ──▶ Проверка шлюзом ──▶ docker exec (песочница)   │
        │                                                    │
        │  [TOOL_RESPONSE_TRUNCATED] начало+конец вывода ────▶│
        │◀──────────────────────────────── [SEND_FULL] ──────│
        │  [TOOL_RESPONSE_FULL] полный вывод ────────────────▶│
        │◀──────────────── [FINISH] {summary, findings} ─────│
        │  конечный — синтезирует отчет, если модель забыла   │
```

Две детали делают этот механизм надежным даже на *маленьких* моделях: вывод утилит **проверяется на угрозы и очищается от ANSI-символов** перед отправкой модели (см. [Безопасность на уровне контента](#безопасность-на-уровне-контента)), а если в ответе пропущен начальный тег, он **восстанавливается на основе структуры JSON** (поле `command` → `RUN_COMMAND`, `role`+`subgoal` → `HANDOFF` и т.д.).

**Агент → LLM (теги наблюдений / конвертов) — как агент возвращает результаты:**

| Тег | Значение |
|-----|---------|
| `[TOOL_RESPONSE]` | Команда выполнена успешно; далее следует вывод. |
| `[TOOL_RESPONSE_TRUNCATED]` | Вывод слишком длинный; показано начало и конец. Отправьте `[SEND_FULL]`, чтобы получить весь текст. |
| `[TOOL_RESPONSE_FULL]` | Полный вывод команды, запрошенный через `[SEND_FULL]`. |
| `[TOOL_FAILED]` | Команда выполнена с ошибкой — измените параметры, не повторяйте ее. |
| `[COMMAND_BLOCKED]` | Неверный формат команды или шлюз отклонил цель как находящуюся вне разрешенной зоны. |
| `[DUPLICATE_BLOCKED]` | Вы только что запускали эту команду — выберите другое действие. |
| `[REPEATED_FAILURE]` | Несколько ошибок подряд — смените утилиту/маршрут, перепланируйте или завершите работу. |
| `[STUCK]` / `[ABNORMAL_PATTERN]` | Обнаружен повторяющийся паттерн действий. |
| `[LONG_RUNNING]` | Время выполнения превысило мягкий лимит — ответьте `[CONTINUE]` или `[ABORT]`. |
| `[OUTPUT_OVERFLOW]` | Вывод в терминале переполняет контекстное окно. |
| `[APPROVAL_DENIED]` / `[APPROVAL_TIMEOUT]` | Оператор отклонил или проигнорировал команду, требующую подтверждения. |
| `[PLAN_UPDATED]` / `[BUDGET_WARNING]` | План обновлен / осталось мало шагов до лимита. |
| `[UNKNOWN]` | Агент не смог классифицировать ситуацию — решение за вами. |

**LLM → Агент (теги контроля / действий) — что модель отправляет в ответ (тег, затем JSON-тело):**

| Тег | Тело | Эффект |
|-----|------|--------|
| `[RUN_COMMAND]` | `{command, step_id, rationale, risk_level, findings?, findings_detail?}` | Запустить команду в песочнице. |
| `[UPDATE_PLAN]` | `{steps:[…], reason}` | Обновить план действий. |
| `[FINISH]` | `{summary, findings}` | Цель достигнута. |
| `[HANDOFF]` | `{role, subgoal}` | Делегировать подзадачу профильному субагенту. |
| `[REMEMBER]` | `{key, value}` | Сохранить структурированную память под ключом (никогда не забывается). |
| `[ASK_OPERATOR]` | `{question}` | Блокировка; требуется помощь человека. |
| `[SEND_FULL]` · `[CONTINUE]` · `[ABORT]` · `[STOP_TASK]` | — | Отправить полный вывод / продолжить ожидание / отменить команду / остановить задачу. |

Слабые модели часто забывают написать начальный тег и отправляют только JSON — парсер восстанавливает тег по структуре полей (`command` → `RUN_COMMAND`, `role`+`subgoal` → `HANDOFF` и т.д.), поэтому агент работает стабильно независимо от качества форматирования модели.

### Ядро, независимое от ИИ-модели <a id="ядро-независимое-от-ии-модели"></a>

LLM подключается как **внедряемая и заменяемая зависимость** за интерфейсом с одним методом (`LLM { Chat(...) }`). Ядро разработано с прицелом на *качество работы и широту охвата*, а не под особенности конкретной модели. Небольшая локальная модель (qwen3:8b) используется в качестве рабочего инструмента разработки и стресс-теста: если ядро надежно работает на маленькой модели, оно будет работать и на большой. Подключите более мощную модель, и то же ядро просто *раскроет* свой потенциал шире; менять его код не потребуется.

## Хранилище знаний — двухслойная память + цикл обучения <a id="хранилище-знаний"></a>

Пакет `internal/knowledge` является листовым (зависит внутри системы только от пакета `scope`) и выступает **единственным владельцем модели мира**. Агент, исполнитель, API и все субагенты пишут в одно место — благодаря этому находки агента становятся структурированными, индексируемыми и общими знаниями, а не просто текстом, запертым в контексте одной задачи.

**Два слоя памяти:**

1. **Фактическая (для конкретной сессии)** — таблицы `targets` и `findings`. Каждая находка (finding) хранит происхождение: `source` (`manual` / `agent` / `subagent`) и идентификатор задачи `task_id`, в которой она была получена.
2. **Процедурная (переносимая, без привязки к целям)** — таблица `procedural_memory`. Каждая выполненная команда записывается как *тактика*: `{tool, command_pattern, outcome}`, где адрес/домен цели заменяется на шаблон `<TARGET>` (через `scope.ExtractTarget`), чтобы **никакие данные конкретных целей не утекли** в общий слой. Идентичные тактики группируются с увеличением счетчика `hit_count`. Результат работы (`worked` / `failed`) вычисляется **механически** по коду возврата — этот цикл обучения вообще не зависит от модели.

**Цикл обучения:**

```text
    ┌──────────────────┐   ┌───────────────────────┐   ┌───────────────────┐
    │ агент запускает  │──▶│ исполнитель записывает│──▶│ procedural_memory │
    │ команду          │   │ обезличенную тактику  │   │ утилита·шаблон·   │
    └──────────────────┘   └───────────────────────┘   │ результат·хиты    │
             ▲                                         └─────────┬─────────┘
             │                                                   │
    ┌────────┴──────────┐  ┌───────────────────────────┐         │
    │ node_step        │◀─│ RetrievalStrategy читает  │◀────────┘
    │ внедряет блок    │  │ тактики для текущих       │
    │ MEMORY в промпт  │  │ утилит                    │
    └───────────────────┘  │ ‹ИСКЛЮЧАЕТ уже запущенные │
                           │  в ЭТОЙ задаче команды›   │
                           └───────────────────────────┘
```

Поиск тактик скрыт за интерфейсом `RetrievalStrategy`. Стандартная реализация, `StructuredRetrieval`, представляет собой детерминированные SQL-запросы на основе текущей сессии и утилит недавно выполненных команд — без внешних зависимостей, чисто локально. Полнотекстовый или векторный (embedding) поиск можно будет внедрить позже, **не меняя ядро системы**.

Исключение выполненных команд (EXCLUDES) критически важно: процедурная память служит для **переноса опыта между задачами**, а не для повторения только что сделанных шагов текущей задачи в промпте. Если показать модели только что запущенную команду со словами *"это уже сработало ранее — повтори"*, слабая модель гарантированно уйдет в бесконечный цикл повторения команды, поэтому команды текущей задачи отсекаются.

**Постоянный контекст** — таблица `persistent_context` (`ON CONFLICT DO UPDATE`) хранит долгосрочные воспоминания, живущие дольше одной задачи: схемы исходного кода, графы модулей, документацию. Субагент анализа кода строит и обновляет их через команду `[REMEMBER]` — это наш "умный картограф кода".

## Навыки — декларативные сценарии just-in-time <a id="навыки"></a>

Попытка передать все инструкции в промпте перегружает контекст модели и мешает логике. Пакет `internal/skill` реализует **декларативный реестр**: каждый навык описывается YAML-файлом (`persona/v0.1/skills/*.yaml`) с полями `{name, description, triggers, tools, knowledge}`. Во время работы реестр оценивает каждый навык по числу совпадений триггеров (`triggers`) в целях и запущенных утилитах, внедряя в промпты только **топ-N** самых подходящих инструкций — это легкий и предсказуемый локальный RAG. Навыки **не имеют исполняемого кода**; они лишь делают модель умнее при выборе команд для запуска в *песочнице*. Из коробки идут навыки `recon`, `web` и `source-analysis`. Добавить новый навык можно простым созданием YAML-файла — менять код приложения не требуется.

## Субагенты — ограниченное делегирование <a id="субагенты"></a>

Yummi поддерживает иерархическое делегирование задач. Когда оркестратору требуется глубокая профильная работа, модель отправляет `[HANDOFF]{role, subgoal}`, и узел `handoff` запускает **профильного субагента** — точно такой же графовый конечный автомат, настроенный со своей собственной ролью (persona) и ограниченным набором навыков.

- **Общая модель мира.** Субагенты используют ту же базу данных и хранилище знаний, что и оркестратор, поэтому их находки и тактики автоматически объединяются в общую базу. Именно для этого архитектура хранилища знаний проектировалась в первую очередь.
- **Изоляция токенов.** Субагент работает в собственном цикле; родительский агент получает назад только чистую сводку `Summary` (и находки, записанные в общую базу), минуя все промежуточные шаги общения субагента с моделью.
- **Глубина строго ограничена 1.** Субагенты инициализируются с пустым списком доступных субагентов, поэтому они никогда не увидят и не выполнят команду `[HANDOFF]` — рекурсия и форк-бомбы исключены.
- **Одинаковые права.** Каждая команда субагента точно так же идет по единому пути выполнения → проверка шлюзом → песочница. Субагент имеет те же права, что и оркестратор, но не больше.

Поставляется с ролями `recon`, `web`, `source-analysis`, `reverser` и `source-analyzer` (`persona/v0.1/subagents/*.yaml`). Добавить роль можно созданием YAML-файла.

## TRACE — наблюдаемость агента <a id="trace-наблюдаемость"></a>

Мы сделали логику агента **прозрачной и читаемой**. Граф генерирует типизированные события `ActivityEvent` — `plan · command · command_result · memory_recalled · skill_applied · handoff_started · handoff_completed · finding · context_saved · ask · finish`, которые записываются в таблицу `agent_activity` и транслируются через WebSocket `/ws/events` как поток событий `agent.activity`. События субагентов содержат `parent_task_id`, что позволяет красиво вкладывать их в шаги родительской задачи.

- **Вкладка AGENT на веб-панели** — встроенная лента активности: 🧠 извлечено воспоминание, 📘 применен навык, 🔎 находка, 🤝 передача задачи, 💾 сохранено в память. Вы видите *на какие источники опирался агент*, а не просто сухой текст ответов.
- **Вкладка TRACE на веб-панели** — полный интерфейс наблюдаемости: живой лог шагов (с вложенными субагентами), поиск по Находкам, выученным Тактикам, Постоянному контексту (картам кода), Навыкам и Ролям.
- **API чтения** (read-only): `GET /sessions/{id}/activity`, `/tactics`, `/sessions/{id}/context`, `/skills`, `/agent/roles`.

TUI отображает те же самые блоки активности в реальном времени прямо в консоли.

## Дирижер, валидатор и режимы исходящего трафика <a id="дирижер-валидатор-и-режимы-исходящего-трафика"></a>

- **conductor** (`internal/conductor`) — общается напрямую с Ollama, используя системный промпт роли. **Никаких жестких эвристик на случай сбоя нет**: если LLM не настроен или недоступен, он возвращает `intent: decline` с двуязычным (русский/английский, автоопределение) объяснением причины. Ответы представляют собой структурированные намерения в JSON: `suggest_command`, `start_task`, `explain`, `ask_clarification`, `decline`.
- **validator** — выполняет **только классификацию рисков**, но не принимает решений по сетевому доступу. Риск оценивается на основе возвращенного моделью `risk_level` плюс консервативной базовой оценки (`classifyRisk` поднимает уровень до `critical` только при использовании опасных шелл-операторов). **Никакого вшитого белого списка утилит нет** — чтобы научить агента новому инструменту, отредактируйте файлы знаний в `persona/v0.1/`, а не код реестра.
- **Режим исходящего трафика (egress)** (задается оператором, контролируется шлюзом) — глобальный 3-позиционный переключатель поверх списков разрешенных IP:
  - `block` (по умолчанию, fail-closed) — любой исходящий трафик запрещен.
  - `allow` — исходящий трафик полностью разрешен (домены работают без предварительного резолвинга IP).
  - `ask` — при любой новой попытке выйти в сеть требуется ручное одобрение оператора.
  - **Выбранный режим сбрасывается обратно в `block` (fail-closed) при перезапуске шлюза.**

## Шлюз <a id="шлюз"></a>

Безопасный по памяти уровень контроля политик (`gateway/`, бинарный файл `yummi-gateway`):

- **`policy/`** — `PolicyEngine` (структура `RwLock<HashMap>` со временем жизни TTL); правила блокировки приоритетнее разрешений; режим egress выдает итоговый вердикт `verdict` (`allow` / `block` / `needs_approval`).
- **`network/`** — контроллер Linux/nftables для управления цепочкой FORWARD (требует прав `NET_ADMIN`). Опциональное скрытие сетевых отпечатков: нормализация TTL (`ttl_normalize` против пассивного определения ОС) и рандомизация MAC-адресов.
- **`ipc/`** — Unix domain socket, JSON-фрейминг с префиксом длины (`[4-байта BE длины][JSON]`). Запросы: `check_scope`, `get_status`, `ping`, `add_temporary_rule`, `remove_rule`, `set_egress_mode`, `list_rules`, `get_audit_log`.
- **`audit/`** — SQLite WAL журнал аудита, каждая строка в котором **связана SHA-256 хэш-цепочкой с предыдущей** (защита от изменения логов). Записываются любые добавления/удаления правил сети и смена режимов egress.
- **`watchdog.rs`** — лимит потребления памяти (RSS) + контроль активности процесса; любое нарушение приводит к мгновенной аварийной блокировке сети и завершению работы демона.

Вкладка GATEWAY на веб-панели показывает статус шлюза, активные правила, журнал аудита и переключатель режима egress.

## Песочница <a id="песочница"></a>

Защищенный контейнер Kali: корневая файловая система примонтирована только для чтения, запуск от пользователя `1000:1000`, только права `NET_RAW`/`NET_ADMIN`, флаг `no-new-privileges`. DNS-запросы принудительно идут через шлюз для ведения логов. Точка входа контейнера просто ожидает доступности сокета шлюза и уходит в `sleep infinity` — каждая команда запускается как новый `docker exec`, а не в рамках постоянного терминального процесса.

## Интерфейсы — Web UI и TUI <a id="интерфейсы"></a>

Два визуальных интерфейса работают **через один и тот же API REST/WS** — ни один из них не имеет обходных путей запуска команд:

- **Web UI** (`ui/`, React 18 + Vite, nginx на порту `:3000`) — вкладки: AGENT (чат + лента активности), BASH (интерактивный терминал песочницы по WebSocket), TRACE (наблюдаемость и модель мира), LOGS, GATEWAY, HEALTH.
- **TUI** (`internal/tui`, Charm Bubble Tea) — консоль оператора в терминале: чат с подтверждением команд, отслеживание шагов задачи и та же лента активности (блоки навыков/памяти/находок/субагентов) по WebSocket. Запуск через `yummi --tui` или `make start-tui`.

## Быстрый старт <a id="быстрый-старт"></a>

```bash
make install   # подготовка окружения разработки (Go, Rust, Node, Docker, Ollama)
make build     # сборка CLI + оркестратора + шлюза (UI собирается отдельно)
make start     # проверка Ollama и запуск стека через docker compose
# Веб-панель управления → http://localhost:3000

make start-tui # запуск сервисов и открытие консоли TUI в терминале
./bin/yummi --tui   # (если сервисы уже запущены на фоне)
```

Первый запуск `make start` скачивает модель по умолчанию (`qwen3:8b`, ~4 ГБ).

## Рабочий процесс разработчика <a id="рабочий-процесс-разработчика"></a>

```bash
make build      # CLI + оркестратор + шлюз (БЕЗ сборки веб-интерфейса UI)
make test       # запуск всех тестов: Go (CLI + оркестратор) + Rust (шлюз) + UI (vitest)
make lint       # запуск golangci-lint в корне репозитория и в модуле оркестратора
```

```bash
# Раздельная сборка компонентов
make _build-cli · _build-orchestrator · _build-gateway · _build-ui
make docker-build · docker-orchestrator · docker-ui

# Раздельный запуск тестов
make _test-cli · _test-orchestrator · _test-gateway · _test-ui
make test-agent-live    # e2e-тесты с реальной моделью qwen3:8b и песочницей (пропускается, если она выключена)

# Управление процессами
make dev · dev-ui · dev-orchestrator     # запуск dev-серверов с hot-reload
make force-restart · close               # перезапуск / остановка всего стека и освобождение VRAM
```

В репозитории два модуля Go: **корневой** (`./go.mod`) содержит CLI + TUI; модуль **оркестратора** (`orchestrator/go.mod`) содержит всю логику ИИ, API и выполнения. Тесты в пакете `orchestrator/internal/*` должны запускаться из папки `orchestrator/` (это отдельный Go-модуль). Шлюз написан на Rust; интерфейс покрыт тестами на vitest. **Мы не пишем моки для внутренних компонентов Yummi** — тесты используют реальные базы данных и движки, подменяя заглушками только обращение к LLM.

## Конфигурация <a id="конфигурация"></a>

Переменные окружения оркестратора:

```bash
YUMMI_ORCHESTRATOR_HOST=127.0.0.1   YUMMI_ORCHESTRATOR_PORT=9080
YUMMI_DB_PATH=~/.yummi/sessions.db  YUMMI_HOME=~/.yummi
YUMMI_DOCKER_SOCKET=/var/run/docker.sock   YUMMI_SANDBOX_CONTAINER=yummi-sandbox
YUMMI_GATEWAY_SOCKET=/run/yummi/gateway.sock
YUMMI_OLLAMA_URL=http://localhost:11434    # пусто = дирижер отклоняет любые задачи (без fallback)
YUMMI_OLLAMA_TIER=standard                 # lite | pro | expert | standard
YUMMI_PERSONA_DIR=persona/v0.1
```

Предустановки тира определяют модель, контекстное окно и режим рассуждений: `lite` → llama3.2:3b · `pro` → llama3.1:8b · `expert` → llama3.3:70b · `standard` (дефолт для разработки) → qwen3:8b.

**Сетевой доступ не настраивается в оркестраторе.** Он конфигурируется исключительно в YAML-файле самого шлюза (`scope.allow` / `scope.block` в `gateway/config/default.yaml`) — шлюз является единственным источником правды для сетевого доступа.

## Инварианты безопасности <a id="инварианты-безопасности"></a>

Если вы вносите изменения в Yummi, сохраняйте эти правила:

1. **Fail-closed по умолчанию.** Любые изменения сетевого доступа и nftables должны строго следовать логике "запрещено все, что явно не разрешено". Шлюз устанавливает запрещающие правила до открытия IPC-сокета.
2. **Единственный путь выполнения.** Команды пентеста попадают в контейнер только через `sandbox.Bridge.Exec`. Никогда не создавайте путь выполнения команд на хосте, доступный из вывода агента или LLM. (`internal/mcp` умеет запускать процессы на хосте и потому держится выключенным — его запрещено импортировать в продакшн коде.)
3. **Шлюз — единственный источник правды для доступа.** Оркестратор запрашивает доступ, но никогда не принимает это решение сам.
4. **Режим egress сбрасывается в `block` при перезапуске шлюза.**
5. **Разделение дирижера и исполнителя.** Дирижер знает все о LLM, ролях и рисках, но ничего о том, как физически запускаются команды. Исполнитель знает все о шлюзе, песочнице и запуске процессов, но ничего о чатах и предложениях модели.
