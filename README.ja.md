## Yummiとは <a id="yummiとは"></a>

Yummiは、*「AIが提案し、ゲートウェイが執行する」*という厳格なルールの下で構築された**4つのコンポーネントと1つの代替フロントエンド**で構成されています。AIが実行するすべてのペネトレーションテストコマンドは、必ず1つの場所を経由し、クラッシュ時にも存続するフェイルクローズ（fail-closed）なネットワークポリシーによって制御されます。

```
ユーザー / オペレーター  →  オーケストレーター (Go)  →  ゲートウェイ (Rust, IPC)  →  サンドボックス (Kali Docker)
  Web UI / TUI             コンダクター + エージェント    フェイルクローズ nftables       ツール実行のみ
                           ナレッジ + API                 ポリシーエンジン + 監査
```

- **orchestrator** (Go) — AIコンダクター、エージェントグラフエンジン、ナレッジストア、およびREST/WebSocket APIを所有します。nftablesを直接制御することはありません。
- **gateway** (Rust、バイナリ名 `yummi-gateway`) — サンドボックスから外部トラフィックを開くことができる唯一のコンポーネントです。起動時にデフォルト拒否（`DROP`）のnftablesルールをインストールし、クラッシュした場合でもそのルールがカーネル内に残ります（**フェイルクローズ**）。
- **sandbox** (Kali Docker) — 読み取り専用ファイルシステム、非rootユーザー、`NET_RAW`/`NET_ADMIN`権限のみ。受動的：オーケストレーターがサンドボックスに対して `docker exec` を実行したときのみ動作します。
- **ui** (React 18 + Vite) — ポート `:3000` で動作するWebダッシュボード。`/api/` と `/ws/` をポート `:9080` のオーケストレーターにプロキシします。
- **TUI** (Charm Bubble Tea) — 同一のREST/WS APIと通信する、完全にターミナルベースのオペレーターコンソール（`yummi --tui`）です。

## システムアーキテクチャ <a id="システムアーキテクチャ"></a>

```text
        ┌──────────────────────────────────────────────────────┐
        │          Webダッシュボード   ·   ターミナル TUI       │
        └───────────────────────────┬──────────────────────────┘
                                    │  REST + WebSocket · :9080
        ┌───────────────────────────▼──────────────────────────┐
        │ オーケストレーター · Go                              │
        │                                                      │
        │   API ─▶ コンダクター ─▶ エージェントグラフ ─▶ 実行器 │
        │                            │                         │
        │                            ▼ (共有世界モデル)        │
        │              ナレッジストア: 検出・メモリ            │
        │                            ・コンテキスト・TRACE     │
        └───────────────────────────┬──────────────────────────┘
                                    │  Unixソケット · 長さプレフィックス付きJSON IPC
        ┌───────────────────────────▼──────────────────────────┐
        │ ゲートウェイ · Rust信頼境界                         │
        │ フェイルクローズnftables・イグレス・監査・番犬       │
        └─────────────┬────────────────────────────┬───────────┘
          docker exec │  ◀── 唯一の経路             │ 制限付きイグレス (egress)
        ┌─────────────▼───────────┐      ┌──────────▼───────────┐
        │ サンドボックス · Kali   │      │ 外部ターゲット       │
        │ 読み取り専用・非root    │      │ (ゲートウェイポリシー)│
        └─────────────────────────┘      └──────────────────────┘
```

信号はオペレーター → API → コンダクター → エージェント → 実行器 → ゲートウェイ → サンドボックスという単一の背骨をまっすぐ流れ落ちます。`docker exec`は、ゲートウェイのスコープチェックの下流に位置する、信頼できるプレーンからサンドボックスへ入る**唯一の経路**です。サンドボックスは、ゲートウェイのnftablesルールを通じて*のみ*外部世界と通信します。ナレッジストアは、共有世界モデルとしてエージェントに紐付けられています。

### ネットワークトポロジー

```
yummi_internal (172.20.0.0/24): サンドボックス .10 ・ ゲートウェイ .2 (DNSも兼ねる) ・ オーケストレーター .3 ・ ui .4 ・ docker-proxy .5
yummi_external:                 ゲートウェイ ・ オーケストレーター ・ ui のみ — サンドボックスは意図的に排除されています。
                                外部に出る唯一の経路は、ゲートウェイのnftablesルール経由のみです。
ホストポート: 3000 → ui nginx ・ 9080 → オーケストレーターAPI (localhostのみ)
```

サンドボックス用のDNSはゲートウェイ（`172.20.0.2`）を経由するように強制されているため、すべてのDNSクエリが記録されます。

## 信頼境界 <a id="信頼境界"></a>

これはコードベースにおける**最も重要な不変条件**です：*明示的に許可されるまでデフォルトで拒否する。*

- ゲートウェイは、IPCソケットが開く**前**に、すべてのパケットを破棄（`DROP`）するnftablesルールをインストールします。明示的な `Allow` ルールが適用されるまで、サンドボックスは一切通信できません。
- ゲートウェイプロセスが停止した場合でも、カーネル内の `DROP` ルールは維持されます。システムは**フェイルクローズ**し、解放されることはありません。
- **ブロック（Block）ルールは常に許可（Allow）ルールより優先されます。**
- ペネトレーションテストコマンドがシェルに到達する経路は**ただ1つ**です：`sandbox.Bridge.Exec`（`docker exec --user 1000:1000 <container> /bin/bash -lc <cmd>` を実行）。エージェントが直接 `exec.Command` を呼び出すことはありません。コマンドは実行ストアにキューイングされ、実行器がそれを順次取り出して処理します（ゲートウェイのスコープチェック → サンドボックスでの実行）。エージェント/LLMの出力からホスト側のコマンド経路へアクセスすることはできません。

> ゲートウェイモジュールはホスト上ではなくDocker内で実行され、コンテナ環境のカーネルサポートを利用してポリシーを適用します。Dockerの外側で、macOSホスト上で直接コンパイル済みのバイナリを実行した場合は、ポリシー適用に必要なLinuxカーネルが存在しない状態になります。

## コンテンツレイヤーのセキュリティ <a id="コンテンツレイヤーのセキュリティ"></a>

ゲートウェイは優れた**ネットワークレイヤー**の境界です。しかし、ペネトレーションテストエンジンは、もう1つ別の微妙な攻撃面に直面します。それは、LLMプロンプトに*送り返される* **コンテンツ**です。ターゲットのコマンド出力、スクレイピングしたWebページ、MCPの応答など、これらはすべてオペレーターが作成したものではありません。これらの情報には、プロンプトインジェクション（`ignore previous instructions…`）、C2/promptware命令、データ流出ペイロード、または不可視の双方向（bidi）ユニコードが含まれている可能性があります。Yummiは、このコンテンツレイヤーに対しても同様のフェイルクローズの姿勢を拡張しています。

```text
  ツール出力・メモリ書き込み・スキルファイル                （オペレーター以外が生成）
                       │
                       ▼
             ┌───────────────────┐   threatscan: インジェクション・流出・C2
             │     threatscan    │               ・不可視ユニコードの検出
             └─────────┬─────────┘
        ツール出力     │   メモリ書き込み / スキル読み込み
     (実行中の介入不可)│   （ユーザーの確認が必要）
               ▼                ▼
    ⚠ 警告バナー          ⛔ 厳格モード（strict）でブロック
    "untrusted DATA"
               │
               ▼
          LLMプロンプト
```

- **`internal/security/threatscan`** — 3つのスコープ（`all` / `context` / `strict`）でスキャンを実行する葉パッケージ（標準ライブラリのみに依存）です。ツールの出力は**スキャンされ、警告バナーが付与されます**（検知のみでブロックはしません — オペレーターはコマンドの実行途中で介入できないため）。`[REMEMBER]` による書き込みやスキルのロードは、厳格スコープで**ブロック**され、汚染された出力によってセッションをまたぐ永続的なプロンプトインジェクションが埋め込まれるのを防ぎます。また、出力が脳に届く前に **ANSI/C1 エスケープシーケンス** を除去します。
- **メモリの出所（Memory provenance）** — 監査用として、永続メモリの各行にはそれを書き込んだ主体（`agent` / `subagent`）が記録されます。
- **アーキテクチャ適合性テスト** (`internal/security/invariants`) — ソースツリーを走査し、監査されたシェル境界ファイル以外で `os/exec` が使用されていたり、プロダクションコードで `internal/mcp` がインポートされていたり（休眠ロック）、テレメトリエンドポイントが混入している場合に**ビルドを失敗させる**実行可能なガードです。以下の不変条件は、単なるドキュメントにとどまらずテストによって強制されます。

## エージェントエンジン <a id="エージェントエンジン"></a>

Yummiのエージェントは**単純な `while` ループではありません**。明示的な**グラフ状態遷移マシン**として設計されています。LLMは1ターンに1つのタグ付きアクションを出力し、決定論的なルーターが固定されたエッジテーブルを基に型付けされたノードを走査し、終端ノードに達するまで処理を継続します。この設計により、コンテキストウィンドウの枯渇やアクションの無限ループを防ぐことができます。毎ステップ、会話の履歴に頼るのではなく、完全なタスク状態をプロンプト内に再レンダリングします。

### グラフ状態遷移マシン — ノードとエッジ <a id="グラフ状態遷移マシン"></a>

エンジンは `orchestrator/internal/agent` に配置されています。`graph.go` がノードの集合と `graphEdges` ルーティングテーブル（`node → edge → nextNode`）を保持しており、各ノードはそれぞれ `node_*.go` ファイルに定義されています。

**10個のノード：**

| ノード | ファイル | 役割 |
|------|------|----------------|
| `step` | `node_step.go` | LLMに次のアクションを要求します。タスク状態全体 + スキル + 委譲状態 + メモリをプロンプトにレンダリングし、返された制御タグに基づいてルーティングします。 |
| `tool` | `node_tool.go` | バッファリングされたコマンドの検証、制御、実行。スタックや重複パターンの検出、および長時間実行コマンドの監視を行います。 |
| `consult` | `node_consult.go` | コマンド実行中の確認（例：長時間実行時） — LLMに `[CONTINUE]`/`[ABORT]` を尋ねます。 |
| `retry` | `retry.go` | 指数バックオフを伴うLLM/パースエラーの回復。呼び出し元ノードに戻るか、諦めます。 |
| `summarize` | `node_lifecycle.go` | コンテキストの圧縮：トークン予算が80%以上消費された場合、履歴を要約に圧縮します。 |
| `approval` | `node_lifecycle.go` | オペレーターの承認ゲート（チャネル上でループのgoroutineをブロックします）。 |
| `finish` | `node_lifecycle.go` | 終端：完了 / 失敗 / 停止。モデルが要約を生成しなかった場合は、要約を合成します。 |
| `ask` | `node_lifecycle.go` | 終端：一時停止し、オペレーターに質問します。 |
| `handoff` | `node_handoff.go` | 特定のサブタスクを専門のサブエージェントに委譲し、その要約をフィードバックします。 |
| `remember` | `node_remember.go` | 構造化されたメモリ（例：コードマップ）をナレッジストアに保存します。 |

**巡回経路**（`graph.go` の `Execute`） — すべての稼働ノードは `step` に戻るため、エンジン自体がループ構造になります。終端ノードでのみ終了します。

```text
                     (すべての稼働ノードはSTEPにループバックします)
        ┌────────────────────────────────────────────────────────────┐
        │                                                            │
        ▼               run_command          ok / is_error           │
    ┌─────────┐ ─────────────────────────▶ ┌──────┐ ──────────────────┤
    │  STEP   │                            │ TOOL │                   │
    │ 次のア  │ ◀───── PLAN_UPDATED ─────  │ exec │── 承認が必要 ──────────▶ approval ─▶ STEP
    │ クション│                            │  +   │── 長時間実行 ──────────▶ consult  ─▶ STEP
    │ をLLMに │                            │ガード│── スタック/無限ループ ──▶ consult  ─▶ STEP
    │ 要求    │                            └──────┘
    └────┬────┘
         │  finish ・ 予算オーバー ──▶ FINISH (終端)
         │  ask_operator ・ 停止 ────▶ ASK    (終端)
         │  llm_error ──▶ retry ──▶ (呼び出し元に戻る)
         │  summarize ・ remember ・ handoff ──▶ (STEPに戻る)
         ▼
    各STEPは、過去の生チャット履歴ではなく、完全なタスク状態 (プラン・
    観察結果・スキル・メモリ) をプロンプトへ再レンダリングします。
```

終端ノード（`finish`, `ask`）には出力エッジがありません。`Execute` はこれらに達した時点で停止します。`retry` は、それを呼び出したノードへ動的に戻ります。すべての状態遷移はチェックポイントに記録されるため、クラッシュしたタスクは最後のノードから再開できます。

**ループ防止策は多層的です** (`tool` ノード)：完全一致の重複検知 (`[DUPLICATE_BLOCKED]`)、`A→B→A→B` サイクルを検知するスライディングウィンドウ型スタック検出器 (`[STUCK]`)、ハッシュ値では検出できないセマンティックな近傍重複を捕捉する **tool-thrash** ガード — 例：`ps -ef` / `ps -ejH` / `ps aux` のローテーションを検出 (`[ABNORMAL_PATTERN]`)、および連続失敗時に別のアプローチを強制し (`[REPEATED_FAILURE]`)、最終的にオペレーターに通知して停止するエスカレーション処理。極めて重要なのは、手続きメモリが*現在のタスク内*で既に実行されたコマンドを想起することはないため、学習ループが同じ繰り返し動作を強化することはありません。

### タグプロトコル <a id="the-tag-protocol"></a>

エージェントとLLMは、**角括弧で囲まれた閉じた語彙セット**（`protocol.go` の `Registry` にて定義）で通信します。これは自由記述テキストでもXMLでもなく、独立した行に記述された `[TAG]` と、その後に続くオプションのJSONボディです。レジストリが唯一のソースオブトゥルース（信頼できる唯一の情報源）であり、プロンプトのプロトコル参照仕様はここから自動生成されます。

```text
   エージェント (stepノード)                                LLM (脳)
        │  完全なタスク状態 + スキル・メモリのレンダリング       │
        │  およびプロトコル仕様の提示のあと、尋ねる ─────────────▶│
        │                                                    │
        │◀──────────────── [RUN_COMMAND] {command, risk} ────│
        │                                                    │
        │  検証・スタック/ループチェック・スコープ確認         │
        │  ──▶ ゲートウェイスコープチェック ──▶ docker exec    │
        │                                                    │
        │  [TOOL_RESPONSE_TRUNCATED] 先頭+末尾出力 ──────────▶│
        │◀──────────────────────────────── [SEND_FULL] ──────│
        │  [TOOL_RESPONSE_FULL] 完全な出力 ──────────────────▶│
        │◀──────────────── [FINISH] {summary, findings} ─────│
        │  終端 — モデルが出力を省略した場合はレポートを合成   │
```

このプロトコルは、*小型の*モデルにおいても堅牢に動作させるための2つの特性を持っています：ツールの出力は脳に届く前に**脅威スキャンを受け、ANSIエスケープが除去されます**（[コンテンツレイヤーのセキュリティ](#コンテンツレイヤーのセキュリティ)を参照）。また、先頭のタグが欠落している応答があった場合、**JSONの構造から制御タグを推論**して回復します（`command` フィールドが存在 → `RUN_COMMAND`、`role`+`subgoal` が存在 → `HANDOFF` など）。

**エージェント → LLM (観察・カプセルタグ) — 結果の返送方法：**

| タグ | 意味 |
|-----|---------|
| `[TOOL_RESPONSE]` | コマンドが成功しました。出力を表示します。 |
| `[TOOL_RESPONSE_TRUNCATED]` | 出力が長すぎます。先頭と末尾を表示しています。全体が必要な場合は `[SEND_FULL]` を送信してください。 |
| `[TOOL_RESPONSE_FULL]` | `[SEND_FULL]` によって要求された完全な出力です。 |
| `[TOOL_FAILED]` | コマンドは実行されましたが失敗しました。同じコマンドを繰り返さず、調整してください。 |
| `[COMMAND_BLOCKED]` | 不正な形式、またはゲートウェイによってターゲットがスコープ外として拒否されました。 |
| `[DUPLICATE_BLOCKED]` | まったく同一のコマンドを直前に実行しています。別のコマンドを選択してください。 |
| `[REPEATED_FAILURE]` | 連続して失敗が発生しています。ツールや経路を切り替えるか、再計画するか、終了してください。 |
| `[STUCK]` / `[ABNORMAL_PATTERN]` | 重複したパターンが検知されました。 |
| `[LONG_RUNNING]` | コマンドがソフト制限時間を超えました。 `[CONTINUE]` または `[ABORT]` を選択してください。 |
| `[OUTPUT_OVERFLOW]` | ターミナルの出力がコンテキストウィンドウを圧迫しています。 |
| `[APPROVAL_DENIED]` / `[APPROVAL_TIMEOUT]` | オペレーターが承認制限コマンドを拒否したか、応答しませんでした。 |
| `[PLAN_UPDATED]` / `[BUDGET_WARNING]` | プランが受け入れられました / 残りステップが少なくなっています。 |
| `[UNKNOWN]` | エージェントが状況を分類できませんでした。あなたが判断してください。 |

**LLM → エージェント (制御・アクションタグ) — モデルが返答するタグ（タグの後にJSONボディが続きます）：**

| タグ | ボディ | 効果 |
|-----|------|--------|
| `[RUN_COMMAND]` | `{command, step_id, rationale, risk_level, findings?, findings_detail?}` | サンドボックスコマンドを実行します。 |
| `[UPDATE_PLAN]` | `{steps:[…], reason}` | プランを改訂します。 |
| `[FINISH]` | `{summary, findings}` | 目標達成。 |
| `[HANDOFF]` | `{role, subgoal}` | 専門のサブエージェントにサブタスクを委譲します。 |
| `[REMEMBER]` | `{key, value}` | 構造化されたメモリを指定キーで永続化します（忘れることはありません）。 |
| `[ASK_OPERATOR]` | `{question}` | 進行不能状態。人間に問いかけます。 |
| `[SEND_FULL]` ・ `[CONTINUE]` ・ `[ABORT]` ・ `[STOP_TASK]` | — | 完全な出力を再送 / 待機継続 / コマンドキャンセル / タスク停止。 |

能力の低いモデルは先頭のタグを省略してJSONのみを出力することがありますが、パーサーがペイロードの形状から制御タグ（`command` フィールド → `RUN_COMMAND`、`role`+`subgoal` → `HANDOFF` など）を推論するため、モデルのフォーマット追従性に関わらずエージェントは安定して動作します。

### ブレインに依存しないコア <a id="ブレインに依存しないコア"></a>

LLMは、単一メソッドを持つインターフェース（`LLM { Chat(...) }`）の背後に隠された、**インジェクション可能で交換可能な依存関係**です。コアエンジンは*品質と適用範囲*を優先して設計されており、現在接続されているモデルの個別の能力に依存しません。小さなローカルモデル（qwen3:8b）を開発用の脳および品質ストレステストとして使用しています。コアがこの小さな脳で健全に動作するなら、より大きな脳でも問題なく動作します。より強力な脳を接続すれば、同じコアが機能レベルを*拡張*させるだけであり、コア自体のロジックを変更する必要はありません。

## ナレッジストア — 2層メモリ + 学習ループ <a id="ナレッジストア"></a>

`internal/knowledge` は独立したパッケージ（内部的には `scope` のみに依存）であり、**世界モデルの唯一の所有者**です。エージェント、実行器、API、およびすべてのサブエージェントがこの1箇所に書き込みを行います。これにより、エージェントの発見は1つのタスクに閉じ込められた自由記述テキストではなく、構造化され、検索可能な共有知識となります。

**2つのメモリレイヤー：**

1. **ファクト（エンゲージメントごと）** — `targets` および `findings` テーブル。検出結果（findings）には、`source` （`manual` / `agent` / `subagent`）と、それを生成した `task_id` という出所情報が記録されます。
2. **手続き（ポータブル、ターゲット除去済み）** — `procedural_memory` テーブル。実行された各コマンドは、*戦術（tactic）*として記録されます：`{tool, command_pattern, outcome}`。ここでターゲットのドメインやIPは `scope.ExtractTarget` を通じてリテラルの `<TARGET>` プレースホルダーに置換され、**ターゲット固有の情報が共有レイヤーに漏洩しない**よう保護されます。まったく同じ戦術は `hit_count` によってデデュープ（重複排除）されます。成否（`worked` / `failed`）は終了コードから**機械的に決定**されるため、この学習ループは脳の判断にすら依存しません。

**学習ループの仕組み：**

```text
    ┌──────────────────┐   ┌───────────────────────┐   ┌───────────────────┐
    │ エージェントが   │──▶│ 実行器がターゲットを  │──▶│ procedural_memory │
    │ コマンドを実行   │   │ 除外した戦術を保存    │   │ ツール・パターン・ │
    └──────────────────┘   └───────────────────────┘   │ 結果・ヒット数    │
             ▲                                         └─────────┬─────────┘
             │                                                   │
    ┌────────┴──────────┐  ┌───────────────────────────┐         │
    │ node_step がプロン│◀─│ RetrievalStrategy が現在  │◀────────┘
    │ プトに MEMORY ブ   │  │ のツールに対応する戦術    │
    │ ロックを挿入      │  │ を読み込む                │
    └───────────────────┘  │ ‹現在のタスクで既に実行済│
                           │  のコマンドは除外する›    │
                           └───────────────────────────┘
```

情報の取得は `RetrievalStrategy` インターフェースを介して行われます。標準提供されている `StructuredRetrieval` は、現在のセッションと最近実行されたコマンドのツールに基づいてフィルタリングを行う決定論的SQLです。新しい外部依存関係はなく、完全にローカルで動作します。セマンティック/埋め込み（embedding）による取得戦略は、**コアを修正することなく**後から差し替えることができます。

「除外（EXCLUDES）」のステップは非常に重要です。手続きメモリは**タスク間の知識転送**のためのものであり、現在のタスクの作業内容をそのままプロンプトにエコーバックするためのものではありません。直前に実行したコマンドを *"事前知識 — 再発見せずこれを使え"* として再提示することは、能力の低いモデルをコマンドループへ誘い込む直接の原因となるため、現在のタスクのコマンドは想起対象から除外されます。

**永続コンテキスト** — `persistent_context` テーブル（`ON CONFLICT DO UPDATE`）は、単一タスクのスライディングウィンドウよりも長寿命な永続メモリを保持します：ソースコードの接続マップ、モジュールグラフ、ドキュメントなど。ソース分析サブエージェントは、`[REMEMBER]`（決して忘れないコードマッパー）を介してこれらを構築・更新します。

## スキル — 宣言的ジャストインタイムプレイブック <a id="スキル"></a>

あらゆるプレイブックをプロンプトに詰め込むと、モデルの推論能力が破壊されます。 `internal/skill` は**宣言的なレジストリ**です：各スキルは `{name, description, triggers, tools, knowledge}` を記述したYAMLファイル（`persona/v0.1/skills/*.yaml`）です。実行時にレジストリは、目標や最近使用されたツールにそのスキルの `triggers`（トリガー）がいくつ含まれているかをスコアリングし、**関連性の高い上位N個**のスキルプレイブックのみをプランおよびステップのプロンプトに注入します。これは軽量で決定論的なローカルRAGとして機能します。スキルは**実行経路を導入しません**。サンドボックス内で実行すべきコマンドの選択に関して、脳をより賢くするためのものです。`recon`、`web`、`source-analysis` スキルが標準搭載されています。YAMLファイルを配置するだけでスキルを追加でき、コードの変更は不要です。

---

## サブエージェント — 制限付き委譲 <a id="サブエージェント"></a>

Yummiは階層的な委譲をサポートしています。オーケストレーターが深部での専門的な調査を必要とする場合、モデルは `[HANDOFF]{role, subgoal}` を出力し、`handoff` ノードが**専門のサブエージェント**を起動します。このサブエージェントは、独自のペルソナと制限されたスキルのサブセットで構成された、同じグラフ状態遷移マシンです。

- **共有世界モデル。** サブエージェントはオーケストレーターのストアおよびナレッジストアを共有するため、彼らの発見や学習した戦術は自動的に単一の世界モデルに統合されます。これが、ナレッジストアを最初に設計した理由です。
- **トークンの遮蔽。** サブエージェントは独自のループを実行します。親エージェントには、サブエージェントの内部的なやり取りの履歴ではなく、クリーンな `Summary`（要約）と、共有知識に書き込まれた発見のみが返されます。
- **深さの制限は1。** サブエージェントは空のサブエージェントマップで作成されるため、彼ら自身が `[HANDOFF]` を受け取ったり実行したりすることはありません。再帰呼び出しやフォーク爆弾（fork bombs）は発生しません。
- **同一の権限。** すべてのサブエージェントコマンドは、同じ唯一の実行パス → ゲートウェイのスコープチェック → サンドボックスという流れを経由します。サブエージェントは、オーケストレーターの権限をそのまま持ち、それを超えることはありません。

`recon`、`web`、`source-analysis`、`reverser`、および `source-analyzer` ロール（`persona/v0.1/subagents/*.yaml`）が標準付属しています。YAMLファイルを置くことでロールを追加できます。

---

## TRACE — エージェントの可観測性 <a id="trace-エージェントの可観測性"></a>

エージェントの思考プロセスは**可読**な形で出力されます。グラフは型付けされた `ActivityEvent`（`plan · command · command_result · memory_recalled · skill_applied · handoff_started · handoff_completed · finding · context_saved · ask · finish`）を発行し、これらは `agent_activity` テーブルに保存され、`/ws/events` WebSocketを通じて `agent.activity` としてストリーム配信されます。サブエージェントのイベントには `parent_task_id` が付与されるため、親のハンドオフスパンの下に入れ子状に表示されます。

- **Webの「AGENT」タブ** — インラインのアクティビティタイムライン：🧠 想起されたメモリ、📘 適用されたスキル、🔎 発見、🤝 委譲、💾 記録されたメモリ。エージェントが*何に基づいて行動しているか*が視覚化され、テキストだけを追う必要はありません。
- **Webの「TRACE」タブ** — 完全な可観測性画面：アクティビティのライブ追跡（入れ子になったサブエージェントスパン）に加え、検出結果、学習した戦術、永続コンテキスト（コードマップ）、スキル、ロールを閲覧できます。
- **読み取りAPI**（読み取り専用）： `GET /sessions/{id}/activity`、`/tactics`、`/sessions/{id}/context`、`/skills`、`/agent/roles`。

TUIもこれと同じアクティビティチップをターミナル上にライブで表示します。

## コンダクター、バリデーター、およびイグレスモード <a id="コンダクターバリデーターおよびイグレスモード"></a>

- **conductor** (`internal/conductor`) — ペルソナ駆動のシステムプロンプトを使用してOllamaと直接対話します。**ルールベースのフォールバックはありません**。LLMが未設定またはアクセス不能な場合、自動検出された2ヶ国語（トルコ語/英語）による説明とともに `intent: decline` を返します。応答は `suggest_command`, `start_task`, `explain`, `ask_clarification`, `decline` などの構造化されたJSONインテントです。
- **validator** — **リスクの分類のみ**を行い、ネットワーク範囲の決定は行いません。リスクはモデル自身が指定した `risk_level` と、保守的な構造的下限に基づいて判断されます（`classifyRisk` は、シェルチェーン演算子が存在する場合にのみ `critical` にエスカレートします）。**ハードコードされたツールの許可リストはありません**。エージェントに新しいツールを教えるには、レジストリではなく `persona/v0.1/` ナレッジを編集してください。
- **イグレス（Egress）モード**（オペレーターが設定、ゲートウェイが執行） — IPごとの許可リストの上位に位置する、実行時の3ウェイマスタースイッチです：
  - `block` (デフォルト、フェイルクローズ) — 外部への通信を一切遮断します。
  - `allow` — サンドボックスからのイグレスを無条件で許可します（IP解決なしでホスト名が動作します）。
  - `ask` — 新しい外部送信先への通信が発生するたびにオペレーターの承認を求めます。
  - **このモードはゲートウェイ再起動時に保存されず、常に `block` (フェイルクローズ) にリセットされます。**

## ゲートウェイ <a id="ゲートウェイ"></a>

メモリ安全なポリシー執行レイヤー（`gateway/`、バイナリ名 `yummi-gateway`）：

- **`policy/`** — `PolicyEngine`（TTLによる期限切れを持つ `RwLock<HashMap>`）。ブロックルールは許可ルールより優先され、イグレスモードは最終判定 `verdict`（`allow` / `block` / `needs_approval`）を下します。
- **`network/`** — FORWARDチェーンを管理するLinux/nftables専用コントローラー（`NET_ADMIN` 権限が必要）。オプションで `ttl_normalize`（パッシブOSフィンガープリント検知を回避）や `mac_randomization` などのフィンガープリント隠蔽に対応。
- **`ipc/`** — Unixドメインソケット、長さプレフィックス付きJSONフレーミング（`[4バイト BE 長さ][JSON]`）。リクエスト：`check_scope`, `get_status`, `ping`, `add_temporary_rule`, `remove_rule`, `set_egress_mode`, `list_rules`, `get_audit_log`。
- **`audit/`** — SQLite WALログ。改ざん防止のため、各行は直前の行と **SHA-256でハッシュチェーン接続** されています。ルールの追加/削除、イグレスモードの変更履歴が記録されます。
- **`watchdog.rs`** — RSS（メモリ使用量）制限およびハートビート監視。制限超過時は緊急ロックダウンを実行し、デーモンを終了します。

Webの「GATEWAY」タブでは、ステータス、アクティブなルール、監査ログ、およびイグレスモードの切り替えスイッチが公開されます。

---

## サンドボックス <a id="サンドボックス"></a>

堅牢化されたKaliコンテナ：読み取り専用のルートファイルシステム、 `1000:1000` ユーザーとして実行、 `NET_RAW`/`NET_ADMIN` のみの付与、 `no-new-privileges` 設定。DNSはゲートウェイ経由に強制され、すべての名前解決がログに記録されます。エントリポイントは単にゲートウェイのソケットを待ち受け、起動後は `sleep infinity` を実行します。すべてのコマンドは永続的なシェルではなく、新鮮な `docker exec` コマンドとして個別に実行されます。

---

## インターフェース — Web UI & TUI <a id="インターフェース"></a>

2つのフロントエンドは**同一のREST/WS API**を使用しており、どちらも新しい実行パスを開くことはありません：

- **Web UI** (`ui/`、React 18 + Vite、ポート `:3000` のnginxでサーブ) — タブ：AGENT（チャット + アクティビティタイムライン）、BASH（WSを介したサンドボックスへのインタラクティブ端末）、TRACE（可観測性と世界モデル）、LOGS、GATEWAY、HEALTH。
- **TUI** (`internal/tui`、Charm Bubble Tea) — ターミナル用のシンプルでクリーンなオペレーターコンソールです。提案 → 承認を伴うチャット、エージェントのタスク追跡、およびWebSocketを介したアクティビティタイムライン（スキル/メモリ/発見/委譲の視覚化チップ）を提供します。 `yummi --tui` または `make start-tui` で起動します。

## 設定 <a id="設定"></a>

オーケストレーターの環境変数：

```bash
YUMMI_ORCHESTRATOR_HOST=127.0.0.1   YUMMI_ORCHESTRATOR_PORT=9080
YUMMI_DB_PATH=~/.yummi/sessions.db  YUMMI_HOME=~/.yummi
YUMMI_DOCKER_SOCKET=/var/run/docker.sock   YUMMI_SANDBOX_CONTAINER=yummi-sandbox
YUMMI_GATEWAY_SOCKET=/run/yummi/gateway.sock
YUMMI_OLLAMA_URL=http://localhost:11434    # 空値 = コンダクターはすべてを拒否 (フォールバックなし)
YUMMI_OLLAMA_TIER=standard                 # lite | pro | expert | standard
YUMMI_PERSONA_DIR=persona/v0.1
```

Tierプリセットは、モデル + コンテキストウィンドウ + 思考モードを決定します： `lite` → llama3.2:3b ・ `pro` → llama3.1:8b ・ `expert` → llama3.3:70b ・ `standard`（開発時デフォルト） → qwen3:8b。

**ネットワークのスコープはオーケストレーターの設定項目ではありません。** これはゲートウェイ自身のYAMLファイル（`gateway/config/default.yaml` 内の `scope.allow` / `scope.block`）においてのみ設定され、ゲートウェイが唯一のスコープ決定権を持ちます。

## セキュリティ不変条件 <a id="セキュリティ不変条件"></a>

Yummiに変更を加える場合は、以下を必ず維持してください：

1. **デフォルトでフェイルクローズ。** スコープやnftablesの変更は「明示的に許可されるまでデフォルトで拒否する」ポリシーを維持する必要があります。ゲートウェイはソケットを開く前にDROPルールをインストールしなければなりません。
2. **単一の実行パス。** ペネトレーションテストコマンドは必ず `sandbox.Bridge.Exec` 経由でのみ実行される必要があります。エージェント/LLMの生成内容からアクセス可能なホスト側のコマンド実行パスを絶対に作らないでください。（`internal/mcp` はホストのプロセスを起動するため休眠ロックされており、プロダクションコードからインポートしてはなりません。）
3. **ゲートウェイが唯一のスコープ決定権を持つ。** オーケストレーターは問い合わせを行うのみであり、自身でアクセス可否を決定してはなりません。
4. **ゲートウェイ再起動時、イグレスモードは `block` にリセットされる。**
5. **コンダクターと実行器の分離。** コンダクターはLLM、ペルソナ、リスクのみを知っており、コマンドがどのように実行されるかは知りません。実行器はゲートウェイ、サンドボックス、実行制御のみを知っており、チャットの内容や提案については一切関与しません。
